### 基线 1：AA频率 + 随机森林 (basl-AARF)
- 特征：20 维 AA 频率 + log1p(长度)，共 21 维
- 模型：RandomForest, n=50, max_depth=12, class_weight=balanced
- 验证 Macro F1：**0.1974** | Precision：0.1324 | Recall：0.4965
- 训练耗时：457s | 500 标签全部训练
- 问题：预测正例是真实值的 3.2 倍，精准率极低，模型倾向过预测
- 文件：`basl-AARF.py`，未保存模型

### 基线 2：k-mer TF-IDF + SGD 逻辑回归 (basl-KmerLR)
- 特征：k=3 Hashing TF-IDF，8192 维稀疏
- 模型：SGDClassifier(loss='log_loss')，lr=1e-4，逐标签
- 验证 Macro F1：**0.1818** | Precision：0.1163 | Recall：0.5996
- 训练耗时：1051s | 500 标签全部训练
- 经历两次 OOM：TfidfVectorizer 建词表 → 换 HashingVectorizer；liblinear → 换 SGD
- 结果略差于 AARF，k-mer 哈希碰撞可能损失信息，过预测问题更严重
- 文件：`basl-KmerLR.py`，模型保存至 `models/basl-KmerLR.joblib`

### 基线 3：CNN + one-hot (cnn-onehot)
- 特征：one-hot 编码 (21 通道: 20AA + pad)，max_len=1500 截断/填充
- 模型：MultiScaleCNN，三路并行 1D-CNN (kernel=3/5/7，各 64 通道 × 2 层) → GlobalMaxPool → cat → Dropout 0.5 → FC 500
- 参数量：179,252
- 训练：BCEWithLogitsLoss, AdamW (lr=1e-3, wd=1e-5), ReduceLROnPlateau, patience=10
- 最佳 epoch：47/50
- 验证 Macro F1：**0.0380** | Precision：0.3099 | Recall：0.0271 | AUC：**0.7273**
- Hamming Loss：0.0474 | 预测正例 152,920 vs 真实 574,163（仅 0.27x）
- 训练耗时：2675s (~45min)，GPU RTX 4060 8GB
- 文件：`cnn-onehot.py`，模型保存至 `models/cnn-onehot.pt`

**CNN 分析**：
- CNN 与前两个模型呈现**完全相反**的行为：RF/SGD 严重过预测（Precision ~0.12, Recall ~0.5-0.6），CNN 严重欠预测（Precision 0.31, Recall 仅 0.027）
- Macro F1 只有 0.038，但 AUC 达到 0.727——**模型排序能力是三个里最好的**，问题出在阈值校准
- sigmoid 输出整体偏低，threshold=0.5 过滤掉了绝大多数正例。降低阈值（如 0.1-0.2）可能大幅提升 Recall 和 F1
- Hamming Loss 0.047 是三个模型里最低的，说明 CNN 在标签级错误率上实际优于传统方法
- 改进方向：(1) 验证集上搜索最优 threshold；(2) 增加模型容量；(3) Focal Loss 替代 BCE；(4) pos_weight 调整

### 基线 3.5：CNN 阈值优化 (cnn-threshopt)
- 关键改动：滤波器 64→128；训练后逐标签阈值网格搜索（50 档，验证集 F1 最大化）
- 验证 Macro F1：**0.2265** | Precision：0.2123 | Recall：0.2816 | AUC：**0.7439**
- Hamming Loss：0.086 | 预测正例 975,369 vs 真实 574,163（1.7x）
- 最优阈值全在 0.5 以下（min=0.01, max=0.43, mean=0.105），证实 v1 的 threshold=0.5 严重过高
- 最佳 epoch：50/50（还在上升，可考虑延长训练）
- 结果超过 AARF (0.1974) 和 KmerLR (0.1818)，成为当前最佳模型

**性能调优发现**：
- Windows 下 DataLoader `num_workers>0` 因 spawn 开销反而慢 2 倍，改为 0
- 序列一次性预编码为 uint8 矩阵，数据加载 1400/s → 18,000/s
- 数据中发现非标准氨基酸 X/U/O/B（839 个），映射为 padding，否则 one-hot 崩溃
- AMP 混合精度实测 1.42x 提速
- batch 64/128/256 吞吐相同（~1410/s），GPU 计算饱和，加大 batch 无速度收益
- 提交文件：`submit/submission_CNN_threshopt.csv`，已复制到桌面

### 文献调研：方向筛选（2026-08-15，第二轮）
- 检索渠道：arXiv 最新排序 + Crossref（Bioinformatics 限定），覆盖 2024-2026
- 关键发现与可行性判断：
  - **STAR-GO**（arXiv:2512.05245，本体感知语义嵌入层级集成）→ **不可行**：
    本赛标签匿名化（label_0~499），无 GO 本体映射，本体结构无法利用
  - **PU 学习/生存偏倚建模**（arXiv:2605.06879，正样本-未标注学习）→ 待评估：
    若训练标签视为完整则 PU 无收益；标签为"已知注释"时可能适用
  - **TRCGL-Net 长尾生成增强**（arXiv:2607.00975）→ 待评估：500 标签长尾，
    尾标签合成增强成本高；共现建模方向已被 TCK002b 证伪
  - **Prot2Text-V2**（arXiv:2505.11194，序列→自由文本多模态）→ 不可行：任务形态不符
  - **对比学习微调嵌入**（ProtSent 思路延续）→ **最有潜力**：预训练嵌入退化
    （E001：mean-pooled/CLS 相似度 0.99+ 无区分度）的根治方案，直接补强
    本任务主导特征（邻居特征）——LoRA 微调 ESM2 做序列相似度对比学习
  - **多 k 融合**（k=3~8 缓存全备）→ **低成本高性价比**：CK002 仅用单 k=6，
    多尺度 k 融合（如 k=3+4+5+6 加权）尚未尝试，DeepGOPlus 原文即多 k 组合
  - **BLAST/MMseqs2 检索邻居** → 低优先级：与 k-mer 邻居高度重叠（嵌入
    与 kmer 相关 0.48+ 的先例），性价比不明

  → PU 学习（取决于标签语义）
